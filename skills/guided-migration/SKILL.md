# Guided migration

Start with a rehearsal in a separate Supabase Cloud project the user owns. Ask whether they want a test preview or a test preview and a live cutover plan, if their request leaves that open. Use preview-only when the user is unsure. Use [migrate-vibe-coded-app](../migrate-vibe-coded-app/SKILL.md) for other builders or a self-hosted Supabase target.

## Connect and identify the run

- Prefer Staticbot MCP. Call `get_account_status` to verify the workspace and connections. If MCP is unavailable but the installed [Staticbot API skill](../staticbot/SKILL.md) can authenticate, use its helper and `GET /me`. For missing or invalid authentication, give the relevant step in the [assistant setup](https://www.staticbot.dev/platform/mcp-server#assistant-setup) and wait to retry the account check. If this client cannot connect, give the [dashboard](https://app.staticbot.dev/migrations) and stop before migration intake. Use the agent's secure environment for `STATICBOT_API_KEY` and the dashboard for integration secrets. If the client needs a fresh session, carry forward any migration ID already assigned.
- Some local MCP versions lack the overview, preview evidence or handoff tools. Use the [REST equivalents](../staticbot/references/api-workflows.md#migrations) when a required tool is missing or its schema cannot represent a required approval. Compare the organization IDs from MCP and REST account status before combining the transports. If the shell cannot access the key or an action is unavailable through either transport, give the dashboard link and the step to complete there.
- Resolve an existing run before using the account's new-run `pendingAction`. Fetch a supplied migration ID directly. If asked to resume without an ID, use `list_migrations` and ask for the dashboard run link when the match cannot be verified. After an uncertain create response, find and verify the existing run before retrying. If still uncertain, hand off to the dashboard instead of creating a duplicate.
- Before advancing an existing run, verify the source using its `templateId` and the target using the discovery report's `report.configuration.targetProjectRef`. If discovery is still running, wait for its report. Otherwise, use `statusUrl` to have the user confirm the exact target from the dashboard when the API lacks this evidence. Advance only a confirmed rehearsal on a separate test project with `gatingLevel: GUARDED` and compatible execution. For an existing `STREAMLINED` run, report its current state and require explicit approval before changing its review level. If the level cannot be changed in its current state, monitor or hand off that run without issuing another mutation.
- For a new run, follow the account's `pendingAction`. Send the connection URL it returns for missing source-control or Supabase access and recheck after the user connects it. An explicit request to move the backend answers `CHOOSE_PATH`. Match the current repo against connected repositories before asking for a URL. For native Base44, verify the source connection and selected app with `list_integration_instances` and `list_base44_apps`. Use the integrations page in the account's dashboard for a missing Base44 connection.
- Confirm an empty Supabase Cloud test target for a new rehearsal. If provisioning one, ask for its name, organization and region together. Follow the migration skill for builder-specific export and source access. When using delegated OAuth, require the user's approval for `staticbot:write` before making changes.

## Run the rehearsal

Read [migrate-vibe-coded-app](../migrate-vibe-coded-app/SKILL.md) and use its workflow. Set `gatingLevel: GUARDED` when creating a rehearsal and verify the returned level before making further changes. Once a migration exists, give the user its ID and `statusUrl`. Follow the current `pendingAction`, relay the actual choices and consequences, and require approval of the exact discovery revision before execution. At a blocked step that needs a fresh session, give a continuation prompt that includes the ID and the user's preview or planning intent.

When a secret gate appears, send the dashboard's App secrets link. If the REST response supplies an API endpoint instead of a URL, use the `browserUrl` returned by `GET /migrations/{id}/secrets`. Let the user enter values there. Never use or request credential values in this workflow.

On `REVIEW_TARGET_CONFLICTS`, `REVIEW_TARGET_CLEANUP` or `REVIEW_TARGET_EMPTY`, offer a fresh empty rehearsal project first. Follow the backend's exact action only after any separate cleanup confirmation or browser step. If an official export restore is waiting on target emptiness, keep it pending until the target is ready. Never skip the restore or send its retry as a substitute for clearing the prerequisite.

Use the rehearsal constraints in [phase 0 of the live runbook](../live-migrate-ai-built-app/references/cutover-runbook.md#phase-0--test-migration), even for preview-only runs. Keep the builder backend and production branch in service, use an autogenerated preview domain, and keep target schedules inactive. Any source helper or export needs its own authorization under the migration skill. If the backend switchover gate appears, get the user's approval for a rehearsal option such as `source-primary-supabase-backup` or `handle-myself` when available. A request to repoint production belongs in the later live cutover. Keep Continuous Sync and custom domains outside the rehearsal.

Wait for the migrated preview deployment, independently of migration completion. Let the migration finish preview preparation and reuse its linked deployment. If none was provisioned, request a preview only once backend execution and any rehearsal switchover choice are complete. Read the app URL from preview evidence or deployment details. The deployment's `statusUrl` opens the dashboard. Check that the evidence refers to the test backend and flag unknown backend identity or blocking findings before calling the preview ready. Share the URL, migration ID, findings and remaining steps from the handoff. Tell the user which outbound integrations to sandbox before exercising the preview.

## If the user is preparing a live move

Use [live-migrate-ai-built-app](../live-migrate-ai-built-app/SKILL.md) and its builder companion for rehearsal evidence and the written plan in phases 0–1. Carry forward the existing test run and its verification results rather than starting again. Ask the user to verify key journeys before sizing the cutover window. Record the plan and evidence using the live skill's state file when the client has a working directory. Stop at the plan review. Production pre-staging, a source freeze, the final copy, and DNS or backend changes are a separately authorized continuation in the live migration skill.
