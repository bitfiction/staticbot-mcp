# Guided migration

Start with a rehearsal in a separate Supabase Cloud project the user owns. Ask whether they want a test preview or a test preview and a live cutover plan, if their request leaves that open. Use preview-only when the user is unsure. Use [migrate-vibe-coded-app](../migrate-vibe-coded-app/SKILL.md) for other builders or a self-hosted Supabase target.

## Connect and identify the run

- Prefer Staticbot MCP. Call `get_account_status` to verify the workspace and connections. If MCP is unavailable but the installed [Staticbot API skill](../staticbot/SKILL.md) can authenticate, use its helper and `GET /me`. For missing or invalid authentication, give the relevant step in the [coding agent setup](https://www.staticbot.dev/platform/mcp-server#coding-agent-plugin) and retry the account check after the user completes it. Use the agent's secure environment for `STATICBOT_API_KEY` and the dashboard for integration secrets. If the client needs a reload or fresh session, tell the user to reuse the starting prompt and include any migration ID already assigned.
- Some local MCP versions lack the overview, preview evidence or handoff tools. Use the [REST equivalents](../staticbot/references/api-workflows.md#migrations) when a required tool is missing or its schema cannot represent a required approval, after confirming the REST credential resolves to the same workspace. Apply the same approval and resume rules across transports. If an action is unavailable through either transport, give the user the migration's dashboard link and the step to complete there.
- Follow the account's `pendingAction`. Send the connection URL it returns for missing source-control or Supabase access and recheck after the user connects it. If a delegated OAuth connection is read-only, ask the user to authorize `staticbot:write` before making changes. An explicit request to move the backend already answers `CHOOSE_PATH`. For native Base44, also verify the source connection and selected app with `list_integration_instances` and `list_base44_apps`. Use the integrations page in the account's dashboard for a missing Base44 connection.
- If the user gives a migration ID, fetch that run and check the source, target, and whether the intended preview can safely continue. Resume from its actual state. If asked to resume without an ID, find the existing run with `list_migrations` and ask only when the match is ambiguous. After an uncertain create response, check existing runs before trying another create.
- For a new run, match the current repo against connected repositories before asking for a URL. Confirm the intended test target. Prefer an empty test project and ask for the name, organization and region together if the user needs a new project. Follow the migration skill for builder-specific export and source access. A Lovable Cloud source and a native Base44 source need different setup.

## Run the rehearsal

Read [migrate-vibe-coded-app](../migrate-vibe-coded-app/SKILL.md) and use its workflow, including the default `GUARDED` review level and the exact discovery revision approval. Once a migration exists, give the user its ID and dashboard link. Follow the current `pendingAction` and relay the actual choices and consequences. Browser-only steps use the URL supplied by Staticbot. If this test target contains conflicts, offer a fresh empty project. Never treat selecting a target or choosing a strategy as permission to start writes or erase data.

Use the rehearsal constraints in [phase 0 of the live runbook](../live-migrate-ai-built-app/references/cutover-runbook.md#phase-0--test-migration), even for preview-only runs. Keep the builder backend and production branch in service, use an autogenerated preview domain, and keep target schedules inactive. Any source helper or export needs its own authorization under the migration skill. A preview choice cannot authorize a live backend switch, DNS change, or production promotion.

Wait for the actual preview deployment, independently of migration completion. Check the preview URL and retained preview evidence, then read the handoff report. Share the URL and migration ID, what passed, what failed or is unverified, and the remaining manual steps. Tell the user which outbound integrations to sandbox before exercising the preview. If the preview is blocked or its URL could not be checked, say so and give the exact next action.

## If the user is preparing a live move

Use [live-migrate-ai-built-app](../live-migrate-ai-built-app/SKILL.md) and its builder companion for rehearsal evidence and the written plan in phases 0–1. Carry forward the existing test run and its verification results rather than starting again. Ask the user to verify key journeys before sizing the cutover window. Record the plan and evidence using the live skill's state file when the client has a working directory. Stop at the plan review. Production pre-staging, a source freeze, the final copy, and DNS or backend changes are a separately authorized continuation in the live migration skill.
