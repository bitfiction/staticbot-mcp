# Cutover Runbook

Each phase lists steps and an exit criterion. Update the state file as you go. Stop at every exit criterion for the user's go/no-go.

## Phase 0 — Test migration

1. Run [migrate-vibe-coded-app](../../migrate-vibe-coded-app/SKILL.md) end to end into a **separate** target Supabase project. Confirm its project ref differs from the source.
2. At `CHOOSE_BACKEND_SWITCHOVER`, present all options; recommend `source-primary-supabase-backup` or `handle-myself`. Explain that `switch-fully-to-supabase` repoints the builder's own live app once its PR is merged, which is a cutover, not a rehearsal.
3. At `CHOOSE_FRONTEND_DEPLOY`, a Staticbot deployment on an autogenerated domain is fine. Do not attach the production domain yet.
4. Before anyone uses the preview, list copied cron jobs, webhooks, email senders, and payment calls from the migration jobs and the repository. Tell the user which ones can fire against real people from the target, and have them disable or sandbox those in the target first.
5. Present preview evidence from the migration (`worked`, `problems`, `unverified`). Treat `unverified` as not tested, never as passed. Give the user the preview URL and a test list: sign in with two accounts of different roles, read existing records, create/edit/delete a test record, upload and download a file, run the app's critical journeys.
6. Record elapsed times for discovery, data transfer, and the whole run. They size the window.

**Exit:** the user confirms critical journeys pass and every problem is fixed or explicitly accepted.

## Phase 1 — Cutover plan

1. **Hosting target and DNS provider.** Read the migration's frontend deployment (`get_deployment`): `deploymentTarget` and each `dns` item's action. Follow [domain-switch.md](domain-switch.md) to decide which records move and who writes them. Save the domain's current records (the ones that point it at the builder) verbatim in the state file; they are the rollback.
2. **Final-copy strategy.** Present both, recommend the first:
   - **Clean and reuse the rehearsal target** (`clean_migration_target`, scope `PROJECT`, then a new migration into it). The project ref, URL, and anon key stay the same, so the production stack, its certificate, and both website versions can be ready before the window. Requires rehearsing the clean-and-rerun once in phase 2.
   - **Fresh target project.** No leftover state, but the production stack and its certificate are created inside the window, which lengthens it, and only maintenance approach B is possible.
3. **Maintenance approach.** A (maintenance as a version of the production stack, [maintenance-versions.md](maintenance-versions.md)) with clean-and-reuse; B (maintenance published from the builder) with a fresh target, or when A's prerequisites fail. Record the choice.
4. **Freeze plan.** Load the builder sub-skill and fill in the state file's writer table: every writer, its control, how to prove it is stopped, and how to undo it.
5. **Window.** Estimate: drain + final export + transfer (from phase 0 timings) + verification + DNS propagation, plus at least 50% buffer. Fix date, start, end, timezone, the abort deadline (latest time to decide on rollback before the promised end), and who decides.

**Exit:** the user approves the written plan in the state file.

## Phase 2 — Pre-stage (days before the window)

1. **Lower TTL** on the records that will change (for example 300 seconds) at least one old-TTL period before the window.
2. **Production stack (clean-and-reuse strategy).** Create the production stack for the migrated app on the production domain, publishing only the **certificate-validation** records now. The stack's domain is fixed from here on, so confirm the exact hostname with the user first. For Cloudflare Workers, run `recheck_dns_verification` until the certificate is validated.
3. **Approach A: maintenance version.** Follow the pre-stage sequence in [maintenance-versions.md](maintenance-versions.md): deploy and verify both versions and rehearse the swap. Nobody reaches the stack yet, so this is safe. If it fails, switch to approach B.
   **Approach B: builder maintenance version.** Prepare it in the builder (see the sub-skill) without publishing it.
4. **Rehearse the freeze** on the source using the sub-skill's steps and probes, then undo it. Record how long it took.
5. **Rehearse clean-and-rerun** (clean-and-reuse strategy): clean the rehearsal target and run the migration again. Confirm the app version still works against it, through the migration preview.
6. Send the advance notice ([communications.md](communications.md)). Freeze code changes in the builder from the notice until the window ends.

**Exit:** production stack ready with a validated certificate (approach A: serving the maintenance version, swap rehearsed), freeze rehearsed, notice sent.

## Phase 3 — Window start

1. Maintenance on:
   - A: pause Continuous Sync for the project. Confirm with `get_deployment` that the stack still serves the maintenance version. Then change the domain's routing record from the builder to the production stack (push via `push_dns_to_cloudflare` only when the user authorizes it and the item offers it; otherwise the user edits it at the registrar). Check the domain serves the maintenance page over HTTPS.
   - B: the user publishes the maintenance version from the builder.
2. Post the maintenance status message.
3. Wait out the drain period agreed in the plan. Users with cached DNS or open tabs can still reach the old app during this time. That is why the freeze below is required.
4. Apply the source freeze (sub-skill). Run every failed-write probe and record the results and timestamp. Pause the builder's scheduled jobs and automations.
5. Record the "source writes stopped" timestamp.

**Exit:** every writer in the table shows a recorded failed-write probe. Otherwise stop: do not take the final copy.

## Phase 4 — Final copy

1. Trigger a **fresh** source export as the sub-skill describes (a rehearsal export is stale).
2. Clean the final target if reusing it (`get_clean_target_plan`, then explicit confirmation of the scope and `confirmationProjectRef`, then `clean_migration_target`), or select the fresh target.
3. Create the final migration via migrate-vibe-coded-app. Follow `pendingAction` as usual. At the switchover gate, present the options. `source-preview-supabase-prod` fits users who will keep building in the builder. `handle-myself` fits users who are leaving the builder.
4. Apply the sub-skill's post-copy repair (for example, undoing freeze grants that travelled inside a database export).
5. Keep target cron jobs, webhooks, and outbound email disabled until reopening.

**Exit:** migration `COMPLETED` with every skipped or failed job explained to the user.

## Phase 5 — Verify

1. Present the preview evidence of the final migration. Any `problems` entry marked blocking (for example a grant gap) is a no-go until fixed.
2. Compare row counts per table or entity and the newest records between source and target. Compare file counts per bucket.
3. The user signs in with real test accounts through each supported login method, checks that one user cannot see another user's data, and runs the critical journeys on the final migration's preview URL. With approach A the real domain shows maintenance until reopening. With approach B it still points at the builder.
4. Confirm that integration callbacks (OAuth redirect URLs, payment webhooks, email links) point at the production domain.

**Exit:** the user records go. On no-go before the abort deadline, fix and re-verify. After the deadline, run the pre-write recovery below.

## Phase 6 — Switch and reopen

1. The user approves reopening.
   - A: `rollback_website` to the recorded app version (`V_app`), then poll `get_deployment` until complete. No DNS change.
   - B: change the domain's routing record to the production stack (same method as phase 3). For Cloudflare Workers, `recheck_dns_verification` must show both statuses `active`. For AWS, confirm HTTPS on the domain serves the new build.
2. Immediately load the app on the real domain and complete one login and one read. If it fails, go back to maintenance (A: `rollback_website` to `V_maint`) and use the recovery rules.
3. With the app confirmed on the real domain, Enable target cron jobs, webhooks, and email, and replay queued events once. Record the time the target became authoritative.
4. Send the completion notice.

## Recovery

- **Before the first production write to the target:** keep maintenance up (A: the stack keeps serving `V_maint`), restore the saved builder routing records, lift the source freeze in the order the sub-skill gives, verify the old app, re-enable source jobs, and send the delay notice.
- **After production writes reached the target:** go back to maintenance, keep the target data, and prefer a fix forward. Returning to the source requires reconciling new records by hand. Explain this to the user; never just flip DNS back.

## Phase 7 — Aftercare

- Watch sign-in failures, errors, uploads, and support messages for the agreed observation period (at least one normal business cycle).
- Keep the source frozen for the agreed recovery period, then retire it or turn it into a development environment. It holds real customer data, so treat it accordingly.
- Restore the normal TTL. With approach A, re-enable automatic website updates if wanted and resume Continuous Sync in the chosen mode.
- Continuing in the builder: set up Continuous Sync with [sync-vibe-coded-app](../../sync-vibe-coded-app/SKILL.md). Migrated apps start with manual promotion of each health-checked frontend preview. Backend changes apply to Supabase when a sync runs, so prefer additive schema changes. Leaving the builder: disable its publishing and develop from the repository.
- Remove temporary export helpers from the source once the recovery period ends.
